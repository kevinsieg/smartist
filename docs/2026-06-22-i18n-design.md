# i18n — three-language support (EN default, FR, DE)

Date: 2026-06-22
Status: Design approved, pending spec review

## Goal

Serve the whole app in English (default), French, and German. Detect the
visitor's language on first visit from the browser; remember the choice
thereafter. Let users pick a language (flag selector) in `/profile` and from a
global switcher. Supporting three languages must not increase page weight or
cause a flash of untranslated content.

## Decisions

| Question | Decision |
|----------|----------|
| Scope | Whole app, **except `stage.html`** (stays English — it has no `common.js`). |
| First-visit detection | Browser language (`navigator.language`), client-side only. |
| Persistence | `localStorage` only — no DB/API/schema change. |
| Switcher location | `/profile` selector **and** a global switcher in the injected footer (works logged-out). |
| Switch behaviour | Store choice, then **reload the page once**. |
| Out of scope (YAGNI) | Per-user DB persistence, geo-IP detection, `Intl` date/number localization, translating emails / PDF export, `stage.html`. |

## Architecture

### Locale files
- `app/i18n/en.json`, `app/i18n/fr.json`, `app/i18n/de.json`.
- Flat keys grouped by area: `nav.songs`, `profile.email`, `common.save`, etc.
- **English is the source of truth.** French and German generated by Claude, to
  be reviewed by a native speaker before merge.
- All three files must contain the **same key set** (enforced by a parity test).
- Served as static CDN assets with a `?v=<n>` cache-bust query, like the
  existing CSS/JS versioning.

### Helper (added to `common.js`)
Roughly 60 lines, no dependencies:

- `getLocale()` — returns the active locale using precedence:
  `localStorage['smartist_lang']` → `navigator.language` matched to `en|fr|de`
  → `'en'`.
- `t(key, vars)` — looks the key up in the loaded dictionary; interpolates
  `{var}` placeholders from `vars`; falls back to the key string (and warns in
  dev) when missing.
- `applyTranslations(root)` — walks `root` for:
  - `[data-i18n="key"]` → sets `textContent` to `t(key)`.
  - `[data-i18n-attr="placeholder:key;aria-label:key2"]` → sets each named
    attribute to `t(key)`.
- `setLocale(locale)` — stores the choice in `localStorage`, sets
  `document.documentElement.lang`, then reloads the page.

### Dictionary loading (performance + no-flash)
- **Only one locale dictionary is ever loaded.** Three languages add no page
  weight.
- **EN (default):** no network at all. The existing English text stays inline in
  the HTML as the natural default, so `applyTranslations` is a no-op for EN and
  there is never a flash.
- **FR/DE repeat visit:** the dictionary is cached in `localStorage`
  (`smartist_i18n_<locale>_v<n>`), read **synchronously** in `injectShell`, and
  applied before first paint — no flash.
- **FR/DE first cold visit:** one small JSON `fetch`. The existing
  `opacity:0 → fade-in on DOMContentLoaded` mechanism in `injectShell` is gated
  on the dictionary being ready, so there is still no flash.

## Markup conventions

- **Static HTML text** → `data-i18n="key"`, with the current English text left
  inline as the default/fallback.
  ```html
  <label data-i18n="profile.email">Email</label>
  ```
- **Attributes** (placeholder, aria-label, title, alt) →
  `data-i18n-attr="placeholder:profile.pwNew"`.
- **JS-generated strings** (innerHTML, toasts, validation messages, the injected
  nav/footer) → `t('key')`.

### Shell handling
`injectShell()` builds the nav and footer with `data-i18n` keys (English text
inline), then calls `applyTranslations()` on the header/footer. For EN this is a
no-op; for FR/DE it applies the cached (or freshly fetched) dictionary before
the fade-in.

## Language switcher UI

- **Footer (injected shell):** compact flag dropdown, present on every
  `common.js` page including logged-out marketing pages. Three small **inline
  SVG flags** (EN/GB, FR, DE) — no new dependency, crisp cross-platform.
- **/profile:** a labelled flag selector row with the same three options.
- Both call `setLocale()`.

## Rollout (phased — whole-app extraction is large)

1. **Phase 1 — infrastructure.** Helper in `common.js`; `en/fr/de.json`
   skeletons; footer switcher; profile selector; `<html lang>` wiring. Verified
   on the shell (nav + footer), `/profile`, and the landing page.
2. **Phase 2+ — page-by-page extraction.** Each page (its HTML **and** its JS
   together) gets `data-i18n` / `t()` markup, with keys added to all three
   locale files. Each page is independently verifiable. The implementation plan
   enumerates every page (all `common.js` pages; `stage.html` excluded).

## Testing

- **Unit (`tests/unit.js`, runs in CI):**
  - `getLocale()` precedence: stored locale wins; else browser language maps to a
    supported locale; else `en`. Includes unsupported-browser-language → `en`.
  - `t()`: returns the translated string, interpolates `{var}`, and falls back to
    the key when missing.
  - Locale-file **key parity**: `en`, `fr`, `de` expose an identical key set.
  - (Helper functions factored so they are testable in Node without a DOM —
    pure functions take the stored value / navigator language / dictionary as
    arguments.)
- **Manual / visual:** switch each language on key pages; confirm no flash,
  persistence across reload and SPA navigation, and that `<html lang>` updates.
